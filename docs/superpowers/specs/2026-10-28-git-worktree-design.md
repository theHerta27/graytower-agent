# 灰塔：用 Git 工作树管理修复任务

日期：2026-10-28。状态：设计待确认，尚未改动产品代码。

独立设计审查已完成：补齐人工解决合并冲突的操作路径后，复查无剩余重大设计疑问；这不代表实现或验收已经完成。

## 为什么改

用户希望复用 Git 管理代码副本、版本、差异和合并，把开发工作集中到 Agent 工具、检查和交付上。每个修复任务应拥有独立工作树，Agent 修改后经过真实检查，用户审阅后才合入开发分支；原项目发生变化时不能沿用旧审批。

这次是同一个灰塔项目的工程改造。保持 LangGraph＋LangChain 单 Agent、项目记忆、资料检索、模型调用记录和 Docker 检查。开发基线为 `cb9d0bd`，当前 `feature/reliable-game-agent` 工作目录干净。10 月 27 日真实实验及失败记录保持历史含义；本次不新增收费模型调用。

## 已核对的现状

- `ProjectWorkspace.create` 从 Git 提交读取允许的文件，写入普通目录；`baseline.json` 保存文件内容，`difflib` 生成差异。
- 编辑通过文件 SHA256 检查过期内容，`edits.sqlite` 保存操作意图和完成状态。文件落盘后丢失确认时，会核对文件实际内容，不盲目重写。
- `CheckJobs` 保存不可变输入，测试结果绑定文件快照、执行器、镜像和检查定义。Docker 得到限定范围的归档，不得到源项目或 `.git`。
- `Adoption.apply` 在用户采用时复查候选、检查结果、原项目 HEAD、未提交修改及目标文件内容，然后逐文件写回；不会 Git 提交。恢复也逐文件进行，有后续编辑则拒绝覆盖。
- 页面当前明确写着“不自动提交 Git”，因此完整 Git 流程会改变一个用户可见行为，必须同时更新说明和确认页面。
- 旧任务、付费范围和检查证据大量存在，不能原地批量迁移、重封或改写。

## Approaches：考虑过的办法

1. **只换副本创建方式。** 新任务使用工作树，但采用和恢复仍逐文件覆盖。改动较小，保留全部旧体验；仍要维护自定义差异、覆盖和恢复，不能兑现完整 Git 流程的解释。
2. **工作树＋Git 提交、合并和撤销（推荐）。** 新任务使用独立分支与工作树。准备交付时生成固定提交，Git 试合并原分支最新版本；检查合并结果，用户确认后合入；撤回产生新提交。改动涉及 workspace、交付服务、API、页面和测试，但标准版本管理交给 Git。

用户已经选择采用 Git 工作树。推荐第 2 种；本设计的确认同时确认“采用会产生 Git 历史，撤回也产生撤销提交”这一产品变化。

## 新任务如何创建

- 继续要求选定普通 Git 项目根目录和一个可解析的起始提交；自动交付要求明确的目标本地分支，不猜测远端或自动拉取。
- 每个任务创建唯一的 `graytower/task-<id>` 分支与独立工作树，记录原项目路径、Git common dir、任务分支、目标分支、起始提交及工作树身份。
- 先验证文件范围和大小，再以 `git worktree add --no-checkout` 创建。使用工作树专属的稀疏检出，只物化原有允许读取的文件；不能默认把仓库内的 `.env`、无关资料等写入候选目录。
- 模型仍只能使用已有受限工具。读范围、写范围、路径检查、链接检查、文件大小限制继续生效；Git 工作树不是操作系统沙箱。
- `.git` 是 Git 管理文件，业务快照、模型材料和 Docker 归档均排除它。程序核对它确实指向本任务登记的工作树，不把任意 `.git` 文件当可信元数据。
- Git 子进程显式绑定 cwd 和参数；不用 shell 拼接路径。工作树专属配置不得改变其他工作树的检出范围或换行行为；内部操作不执行用户 hook、外部 diff/textconv 或隐式签名程序。
- 同一工作树只能有一个灰塔写操作进行；任务运行中不能准备合并、切换基线或清理。锁覆盖 CLI 和服务进程，而非仅一个线程。

## 修改和差异

- 保留 `read_file`、`replace_text`、`write_file` 的现有接口、文件指纹检查和操作记录；Git 不代替工具权限和单次操作恢复。
- 新模式的初始文件可从固定 Git 提交读取，不再另存一份完整 `baseline.json` 作为新模式的权威基线。
- 差异由 Git 生成，覆盖新增、修改、删除及无末尾换行文件；提交只包含允许修改的文件。
- 检查未授权的已跟踪改动、未知新增文件、暂存内容和分支/HEAD 被外部改动，不能因为使用 Git 而放宽范围。
- `snapshot()` 继续向工具和 Docker 提供原有有界文件结构，避免无关重写 Agent/检查协议。完整 Git tree 身份另行记录，不能把局部文件快照说成整个仓库的测试证明。
- 创建内部提交使用明确的服务身份（例如 Graytower Agent），不把模型操作伪装成人类手写提交。任务分支留在本地，不自动推送。

## 准备合并、检查和审批

目标是让用户审批的内容与真正采用的内容一致。

1. 用户选择“准备合并并检查”。先确认任务无运行中的模型/编辑，候选范围合法；原项目在登记的目标分支、没有未提交的已跟踪修改，目标路径不存在会被覆盖的未跟踪文件，也没有未结束的 Git 合并等操作。
2. 将当前候选固定为提交 C。记录原分支当前提交 T；创建任务时的 B 永久保留，不因为合并准备而改变旧模型范围、知识版本或证据。
3. 使用 Git 的合并算法计算 T 与 C 合并后的内容。推荐 `git merge-tree --write-tree`，它不改原项目工作目录和暂存区。不自动选择冲突的一边，不调用收费模型解决。冲突处理采用下文明确的独立交付工作树流程，首版不内置冲突编辑器。
4. 无冲突时生成一个固定的合并提交 M，第一父提交为 T，第二父提交为 C；在独立的交付工作树中检出 M。Agent 候选分支仍保留，避免试合并改变其既有上下文。
5. 对 M 中允许范围的实际文件运行现有 Docker 检查。合并前候选的旧结果不能直接充当这次合并检查。首版准备交付默认要求完整 `rules` 检查通过；已有的、适用于本次快照的可信失败结果仍阻断采用。
6. 展示 T→M 的实际差异、目标分支、检查结果，以及“确认后会合入 Git 提交”的说明。审批保存准备记录 ID、T、C、M、文件快照/完整 Git tree 身份、检查定义及回执身份。
7. 用户同意后，服务端再次核对目标分支/HEAD、目标工作目录、候选内容、准备记录和检查证据。任何一项变化就使原审批失效，要求重新准备、检查和审阅。
8. 用 Git 将目标分支快进到已批准的 M（`git merge --ff-only <M>`），不在最终写入时临时创建另一份未经审阅的合并内容。目标变化而无法快进时停止，保留已有修改。

最终采用使用 Git 正常工作目录更新流程，不允许对一个正在检出的分支直接 `update-ref` 后再手写覆盖文件，以免工作目录和分支指向不一致。`update-ref` 带旧值校验可用于灰塔专属任务引用。

### 冲突后怎样继续（实施者提出的选择）

独立设计审查指出，不能一边拒绝候选分支被外部改动，一边要求用户在该分支手工 merge/rebase。因此，人工解决冲突发生在另一个交付工作树中，原候选保持不变：

- 在固定 T 上创建只用于此次准备的交付工作树，执行 Git 的 `merge --no-commit --no-ff C`，保留正常的冲突文件与索引状态。原项目与 Agent 工作树均不改动。记录此目录用途和 T/C，使用前述受限检出与路径检查。
- 页面给出冲突文件、交付目录和操作说明。用户用自己的编辑器处理冲突、用 `git add` 标记已解决，不在该目录自行提交、切换分支或 rebase；然后点击“检查冲突处理结果”。这不是允许 Agent 修改交付工作树。
- 服务端检查原项目仍为 T、候选仍为 C，交付工作树身份、HEAD 和 MERGE_HEAD 符合准备记录，索引没有未解决项、文件内容与暂存内容一致。只接受原有可编辑范围内的人工修复；范围外文件必须保持 Git 计算得到的合并内容，不能把手改测试当作解决冲突。
- 保存人工处理记录后，固定为父提交 T/C 的 M；重新执行真实检查、展示 T→M 差异并请求最终审批。消除 Git 冲突不等于游戏规则已经正确。
- 任意版本变化或用户自行创建了其他提交，当前准备失效；保留人工改动和诊断，重新准备时不能强制删除这份目录。用户可以导出改动后明确清理，再按新版本处理。

这项选择只补齐冲突后的操作路径，不新增网页内的代码编辑器或自动解决冲突的 Agent。

## 并发和恢复的实际边界

- 灰塔自身的交付操作按仓库串行；多进程通过同一个锁协调。用户审批期间不长期持锁，采用时重新取得锁和复查。
- Git 合并与索引锁、审批版本检查共同保护常规 Git 操作。不能宣称能阻止任意编辑器在最终检查与磁盘写入间直接改文件；首版仍是本地受信任开发场景，不扩大为任意并发写者的严格事务系统。
- 采用前保存持久操作 ID、T 和 M。合并成功但响应/记账中断后，重新查询实际 HEAD：为 M 且工作目录与提交一致，补记成功；仍为 T，可重新核对后续执行；为其他提交或工作目录不一致则停止并报告待人工核对。不能创建第二个合并或强行回退。
- 不把 SQLite 事务说成 Git 引用与多个文件之间的原子事务。保存原始错误与中断状态。

## 撤回和清理

- 新模式的“撤回”产生一个撤销提交，不重写历史或 `reset --hard`。首版要求目标仍停在该次采用的 M 且工作目录干净；如果已有后续提交/编辑，拒绝自动撤回并说明原因，保留用户后续工作。
- 撤销内容先在独立工作树准备（撤销 M 相对于第一父提交的改动），展示差异、检查，再由用户确认；执行前同样复查版本。
- 放弃/清理是显式操作。仅清理属于本任务、已登记的工作树，使用 `git worktree remove`；保留任务记录、检查回执和可追溯提交引用。
- 有未完成模型运行、编辑、检查或交付操作时拒绝清理。未知/未登记路径、额外人工改动不强制删除。创建一半失败时只回收本次确实创建的资源。
- 已归档任务可以看报告和差异；不静默重建一个新副本冒充原工作树。

## 旧任务兼容

- 新建任务默认 `git_worktree`。读取旧 `development-project-v1` 时继续走现有 snapshot 模式，界面明确标识；旧任务的来源、基线、检查和结果不改变。
- 保留旧采用/恢复服务来读取和处理原有记录。旧任务不自动变成 Git 提交，不批量重写 local-data。
- 新模式在 metadata 与交付 API 中明确版本。外发/模型范围绑定工作区模式及所需身份，不能拿旧批准范围运行另一种后端。
- 历史收费实验只读。新的工程验收使用临时仓库及脚本模型，不复用旧模型费用额度。

## 页面和使用方式

- 任务页展示“Git 工作树”、任务分支、起始版本，允许查看实际目录。
- 交付入口改为“准备合并并检查 → 查看合并结果 → 确认合入目标分支”。检查中、冲突、检查失败、版本已变化时清楚显示原因。
- 审批期间内容变化必须关闭旧准备状态；服务端也要验证，不能只靠按钮禁用。
- 明确区分候选检查与准备合并后的检查，不让旧绿色结果继续代表新版本。
- 旧任务仍显示旧的“写回文件、不自动提交”说明。
- 撤回按钮说明“会新增撤销提交”。清理不删除证据。

## 必须验证的场景

使用真实临时 Git 仓库验证，不只 mock Git 命令：

1. 两个任务工作树互不改写，源项目内容和当前分支保持原样；登记分支/工作树可由 Git 查到。
2. 未授权文件（含已跟踪 `.env`）、`.git` 不进入模型输入或 Docker 归档；只读测试无法被 Agent 改成通过。
3. 新增/修改/删除/无末尾换行正确 diff；编辑冲突和中断重放仍正确。
4. 原分支无变化时，准备/真实检查/审批/合入/撤回走通，Git 历史与原始字节可核对。
5. 原分支已有无文本冲突的新提交：合并保留两边内容，检查针对合并后的代码。
6. 同文件冲突：停止自动处理，不丢任何一边；在独立交付工作树人工处理后，必须重新检查和审批。未解决、漏暂存、修改只读文件、私自提交和原项目漂移均拒绝接纳，不假报已合入。
7. 审批前后原分支推进、分支切换、未提交修改、候选又变、检查定义变化，都拒绝过期审批。
8. Git 合并完成后进程中断/回执丢失：再执行不会重复合并；原项目有后续提交时不错误回退。
9. 新增撤销提交，不改历史；有后续编辑或提交时拒绝自动撤销。
10. 创建失败、放弃、清理、中断、路径被替换、Git 指针被改、旧任务打开都能明确处理。
11. 前端/API 相同版本审批；真实 HTTP 流程与实际 Git 引用相符。
12. 临时游戏 clone 上走一次脚本模型→工作树修改→真实 Docker→准备合并→审批→Git 合入→撤销。新增收费调用为 0，不能称为新的真实模型质量评测。

运行相关 Python 回归、前端测试和生产构建，再跑完整 Python 回归。新失败保留记录，修复后重跑受影响部分。实施后独立代码审查并核查实际演示结果。

## 工作量和实施边界

改造前基线已在 2026-10-28 运行：使用现有项目解释器执行 `python -m unittest test_development_workspace test_development_adoption test_development_checks -q`，35 项通过，28.389 秒。该结果仅说明原实现的相关测试通过，不代表新工作树功能已经实现或验证。

这是中等规模工程改造，主要难点是新旧任务并存、审批失效、Git 合并中断与撤回，不是调用 `worktree add` 本身。先完成 Git 工作区与兼容，再交付合并/撤回与页面，最后运行真实 Git/Docker 演示。内部步骤持续推进，不逐函数请求用户批准。

设计待确认后进入实施计划；全部验证在临时仓库/游戏副本进行。产品支持用户以后主动采用修改，但本次开发不把演示改动合进原游戏，不运行付费模型，不自动推送或发布博客。
